Each secret is sealed to its own key, `secrets/<name>` (or `secrets/scoped/<scope>/<name>`), so one secret can be shared without the others. The content key is wrapped once, to that key only, never also to the network key. Reads still open secrets sealed before this change, including ones written without AAD, until they are migrated. A reader holding only one secret's key gets `legacy_envelope` / `LEGACY_ENVELOPE` for such an older copy. `secretKeyPath`, `parseSecretKeyPath` and `secretReadPermissions` build that key and the grant that reads one secret.

`vault.resealToKey(key, keyPath, { dryRun })` moves one record onto its own key: it seals a new copy, checks it opens to the same bytes, and overwrites only if the record is unchanged (`ifMatch`). Any failure keeps the old copy.

Breaking for node-sdk: `secrets.get` and `secrets.getEntry` no longer ask the wallet for missing authority. Pass `requestPermission: true` for a read the user started. Without a live grant on the secret's own key the read is `DECRYPT_DENIED` with `permissionHint` naming that key, and a node refusing that key gives the same code. `namedKeyOnly: true` opens only a copy sealed to the secret's own key. Both are on the new `SecretGetOptions`. `put`, `delete` and `list` still ask as before.

web-sdk keeps approved grants for one secret's own key across reloads, like panel grants. In web-sdk, `secrets.get` and `secrets.getEntry` with `requestPermission: true` ask the page's permission prompt for exactly that key on the space's own network, then read once more. That prompt always shows, even after "don't ask for 30 days". A declined or closed prompt returns `PERMISSION_DENIED`, and the next opted-in read asks again. Without the flag they never ask. A node-sdk node restored without a signer no longer reports that it can ask for authority.

A runtime grant or a `delegateTo` delegation on a secret's own key (or keys under `secrets`) lasts 1 hour unless an expiry is asked, is capped at 7 days, and still ends with the session; the returned `delegation.expiry` is the expiry signed. Other `delegateTo` delegations, network-root decrypt included, keep the 30-day default. node-sdk exports the limits as `SECRET_KEY_GRANT_DEFAULT_MS` and `SECRET_KEY_GRANT_MAX_MS`, and `secretKeyGrantExpiryMs(expiry)` applies them. Secret names and scopes are limited to 64 characters (`MAX_SECRET_NAME_LENGTH`, `MAX_SECRET_SCOPE_LENGTH`); a longer one is `INVALID_INPUT`. `resealToKey` throws unless `keyPath` is the record's own secret key.

`delegateTo` of a secret's key needs that key in the signed session: sign in with an explicit `capabilityRequest` that includes `<network>/secrets/` (decrypt, key.create). The default sign-in does not include it. `delegateTo` refuses any `secrets` path that is not one secret's exact key.

A node without per-secret keys (`encryption-named-keys-v1`, any tinycloud-node before the one that adds it) can't take a secrets `put`: node-sdk and web-sdk return `NAMED_KEYS_UNSUPPORTED` (`service: "secrets"`) before any secret permission request, grant or write; an expired session's sign-in may still run first. No secret grant is signed and nothing is saved. `tc secrets put` prints that code with its own exit code, 11. `get`, `getEntry`, `list` and `delete` still work on secrets already stored there. `NAMED_KEYS_UNSUPPORTED`, `NAMED_KEYS_UNSUPPORTED_MESSAGE` and `namedKeysUnsupportedResult()` are exported from sdk-services and sdk-core, and `TinyCloudNode.namedKeysSupported()` reports the node's answer (it reads `/info` once for a restored session). On such a node, node-sdk's sign-in leaves the `<network>/secrets/…` key entries out of the recap it asks the wallet to sign, which the node would otherwise refuse with 401. It only drops them: the rest of the request, a network-root decrypt included, is unchanged, and a node that lists named keys gets the request exactly as composed. Sign-in reads `/info` once, before it builds a request that names secret keys, and not again after the session.

When the node's features can't be checked (a restored session whose `/info` read fails), a `put` fails closed instead of guessing: it returns `NAMED_KEYS_CHECK_FAILED` (`service: "secrets"`, `meta.retryable: true`, "Couldn't reach this TinyCloud node to check that it can save secrets. Nothing was saved. Try again in a moment.") before any secret permission request, grant or write; an expired session's sign-in may still run first. `tc secrets put` prints it with exit 6 (the network exit). `NAMED_KEYS_CHECK_FAILED`, `NAMED_KEYS_CHECK_FAILED_MESSAGE` and `namedKeysPutRefusal(supported)` are exported from sdk-services and sdk-core.

Secret names and scopes are limited to 64 characters, so a secret already stored under a longer name or scope can no longer be read, written or deleted through `get`, `put` or `delete` after this release. It is not hidden: `listAll()` returns it with `nameTooLong: true` and/or `scopeTooLong: true` (the scope as stored), and `list()` includes its name. A `put` of a name over 64 characters returns `INVALID_INPUT` ("This secret wasn't saved: its name is N characters, and names can be at most 64. Choose a shorter name.") before any secret permission request, grant or write, and `tc secrets put` prints the same words with exit 2. `parseStoredSecretCatalogKey`, `secretNameTooLongMessage` and `secretNameTooLongRefusal(name)` are exported from sdk-services and sdk-core; `parseSecretCatalogKey` still returns nothing for such a key. Self-hosted owners who hold such a secret can rename it with the previous CLI first.

The unscoped secret name `SCOPED` is reserved: its key, `secrets/scoped`, is the parent of every scoped key, so `secretKeyPath`, `resolveSecretPath` and the calls built on them throw `Secret name "SCOPED" is reserved.` and the services return `INVALID_INPUT`. A secret already stored under the unscoped name `SCOPED` can no longer be read, written or deleted through `get`, `put` or `delete`. A secret named `SCOPED` inside a scope is not affected.

Details: TC-3801
