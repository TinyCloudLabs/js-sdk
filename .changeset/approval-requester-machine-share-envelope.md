"@tinycloud/share-envelope": minor
---

`@tinycloud/share-envelope/links` now has one state machine for the side that asks OpenKey for an approval (the CLI and Courier, which still use their own loops until they adopt it). Nothing that exists changes, and the package root is untouched.

- `reduce(state, event)` is pure: time and clock skew come in as event fields, and every step returns the effects to run (persist, purge keys, call, sleep, verify, commit, finish). `driveApproval` runs them with an injected clock, store and transport. An entry that is dropped always comes with a purge of the private keys it held, and nothing in an effect or outcome carries a key.
- One table (`RULES`, fed by `classifyReply`) says what each OpenKey answer means. A denied request (HTTP 410 `expired_request` with `status: "denied"`, or the code `request_denied`) ends in `denied` (exit 3), is never reopened and has its entry and keys removed. A plain 410 `expired_request` is `lapsed`. A 400 `invalid_request` on discover is a refusal of the request and never an expiry. A 401 `invalid_proof` on discover stays kept only until the signed expiry plus 30 s, and is exit 12 only when the local clock is more than 45 s off the reply's `Date` header (otherwise the entry is dropped: exit 5, or exit 3 after expiry). A 401 on fetch or ack never drops an approved result: it is kept until its purge time and reports exit 12 (clock more than 45 s off) or exit 7, with `grantSaved: true` when the grant is already saved (a 401 on the ack). An ack that fails after the grant is saved (no answer, or an answer OpenKey should not give) ends `completed` with an `ack-pending` warning and exit 6, entry kept for the next run; at its purge time it ends `completed` with an `ack-expired` warning, also exit 6. The purge time wins over a step that would keep keys: a reply that lands after it purges the entry and its keys instead of keeping or holding it (a reply that was already terminal keeps its own outcome). No keyed entry is kept past its purge time (a key-free acknowledged entry is kept only until its retention date), and a run ends by the signed expiry plus 30 s (one final poll), by the caller's deadline, or, once a result exists, by the 30 s collect grace.
- A resumed approval completes at least one full status check (up to the request limit) before it reports pending, so a slow answer is never reported as pending, and a first check that gets no answer is "unreachable" (exit 6, entry and keys kept). A request created in this run is live by construction, so when the deadline passes before OpenKey answers it returns its link as pending (exit 8).
- `APPROVAL_EXIT` gives one exit number per outcome (0, 3 for expired, gone and declined, 5, 6, 7, 8, 12 clock), and `exitCodeOf` returns 6 for a completed run whose ack failed. Exit codes scripts see, compared with the earlier drafts of this machine (js-sdk #856): a declined request exits 3, not 11; an ack that fails after the grant is saved exits 6, not 0 with a warning (the TC-2378 exit-8 plan). Exit 8 is returned only with the request's expiry and a live confirmation from this run.
- `parseApprovalFile` reads the one v2 format and the two v1 files it replaces (the CLI's array and Courier's single object), keeps every entry (one that cannot be read, repeats an id, or claims a request life above 24 h is set aside, not deleted; the CLI's signing key with its `kid` is read as is), and `sweepApprovalFile` removes entries and their keys once they are past their purge time. An acknowledged entry keeps neither a key nor the approval URL.
- The v2 file has its own name, `approval-pending.v2.json` (`APPROVAL_FILE`), because published CLI versions read `approval-pending.json` as their v1 array without a version check and would fail on v2 content. `loadApprovalFiles` migrates a v1 `approval-pending.json` into the v2 file and deletes the v1 file only after the v2 file is written; `discardApprovalFiles` (logout, the key sweep) deletes both names. Signing out now clears pending approval requests made before the sign-out, including ones left by an older CLI; a sign-in started after it is kept.

Not in this change: the CLI and Courier still print and exit as before, and `collectApprovalResult` and `refuse` are unchanged.
