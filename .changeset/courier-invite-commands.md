Add `courier invite <handle>`, `courier invite list`, `courier invite revoke <invite-id>`, `courier join <invite-link>` and `courier join --resume`.

- `invite` creates a one-time invite for a handle and email address and prints the invite link once. `invite list` shows metadata only. `invite revoke` deletes the invite link and any pending hello or welcome.
- `--tier` is the requested tier. `--tier trusted` asks for trusted status; the paired peer starts strict until the owner confirms by hand. Self-service invites never create a trusted peer.
- `--expect-owner <did>` (a `did:pkh:eip155` DID) records the account the invitee must pair from; a hello from another owner is held with reason `owner-mismatch`.
- `watch` verifies the email credential in each hello: it is signed by the pinned issuer, names the invited address, was issued within the last hour, is bound to the invite's one-time key and has not been used for this invite before. Its subject and the possession proof must also be the courier DID in the hello's pairing artifact, otherwise the hello is held with reason `holder-mismatch`. A hello that passes pairs the peer as strict; `--also-ask` holds it for `invite approve` even then.
- With `--invites-public-dir <dir>` or `COURIER_INVITES_PUBLIC_DIR`, `invite` also writes a non-secret copy of the invite record (`<invite-id>.json`, mode 0640) and `invite revoke` updates its status. The copy holds no address, keys or link ids.
- `join` reads the invite link from `--stdin` or `--file`; the positional form also works but is visible in `ps`. It sends a hello with an optional credential from `--credential-file` or `--credential-stdin`, and waits about 10 minutes for the owner's reply. `join --resume` continues a pending join without sending a second hello.
- Handles may not begin with `_`. Stored peers whose handle begins with `_` are excluded from notice tracking in `watch`.
- The words `list` and `revoke` cannot be invitee handles, because they select `invite` subcommands.
- Revoking an invite does not revoke delegations granted to its one-time key. Those end at their TTL.
- `watch` checks each incoming hello. A hello that fails a check, or whose pairing cannot finish, leaves the invite held and emits an `invite-held` notice. A held invite is not complete: `invite approve` or `invite deny` it. A failed write to the public copy does not change the pairing; the reason code is logged and the next sweep rewrites the public `status` and `completedPeer` from the private record.
- An invite left `consumed` by a crash is recovered on watch startup and on each sweep, once it is at least 10 minutes old. If its hello is still present and valid it is held with reason `internal-error` (one `invite-held` notice). If the hello is gone or invalid it is marked `failed` with reason `hello-lost` (one `invite-failed` notice) and closes at its expiry.
- `invite approve <invite-id> [--tier strict|trusted]` completes a held invite: it pairs the peer, writes one Welcome and marks the invite completed. `--tier trusted` records a trusted request; the peer starts as strict until you confirm trusted status. Retrying `approve` after a failure completes the same pairing without a second Welcome.
- `invite deny <invite-id>` rejects a held invite, writes a rejected Welcome and drops the pending peer.
- `invite`, `invite approve` and `watch` refuse a handle that has an entry in the box's `peers.json` (`<COURIER_HOME>/peers.json`, `<COURIER_HOME>/intake/peers.json`, and the file named by `--peers-file` or, without the flag, `COURIER_PEERS_FILE`), so a new peer never inherits an old entry's trust. `--peers-file` replaces `COURIER_PEERS_FILE` for that command. The named path must be absolute, free of control characters and exist; an empty value, a relative path or a missing file stops the command with an error. Every value `watch --install-systemd` writes into the unit goes through one of two writers: quoted words (`ExecStart=` arguments, `Environment=` assignments) escape backslash, quotes, `%`, newline, carriage return and tab (and `$` in `ExecStart=`) and refuse other control characters; the path directives (`WorkingDirectory=`, `StandardOutput=`, `StandardError=`) refuse control characters, relative paths and a trailing backslash or whitespace, and double `%`. Environment names must be plain variable names. `watch --install-systemd` checks it and writes `COURIER_PEERS_FILE` into the unit. `invite` fails with `peers-entry-exists`; `watch` holds the hello with that reason; `approve` fails with it and the invite stays held. A peers file that exists but is not a readable JSON object, or a named file that has gone missing, refuses with `peers-unreadable`. Remove the entry to continue.
- On every poll `watch` also looks for a hello on each open invite, so a hello written while the watcher was not subscribed is still handled. The hello is consumed first, so it pairs once.
- If `join` finds a hello already stored for the invite that is not the one it wrote (or that it cannot read back), it does not write over it. It polls `out/welcome.json` and pairs only with a Welcome addressed to this courier from the inviter pinned when the invite was accepted. If none arrives before the invite expires (or only Welcomes that do not verify for this courier, which it says with a stable code) it stops with `hello-exists`, also on a `join --resume` after expiry, and says to ask the inviter for a new invite (and to run `courier revoke <handle>` first if that is refused with "already exists"). `join --resume` re-enters the wait and never writes again.
- A new invite from the same inviter replaces the unfinished pairing an earlier failed `join` left behind and drops that join's state. A paired peer under the handle still blocks. `invite revoke` frees a handle whose pairing never started.
- `invite approve` looks for a Welcome that is already out (for example a rejected one left by an interrupted `invite deny`) before it asks the node for a grant, and stops with `welcome-exists` without minting one.
- `invite approve` prints the tier the invite carries.
- `invite approve <invite-id>` first prints the owner and courier DID of the hello that is actually held, why it is held and the owner the invite expected, and requires `--owner <did>` (a `did:pkh` DID or its `0x` address) equal to the held hello's owner; without it, or with another owner, it pairs nothing (`owner-mismatch`). A held invite's public record also carries `heldReason` (one of a fixed set) and `helloOwner`.
- Recovering an invite left `consumed` by a crash now re-holds the hello that was already held, and uses the hello under `in/` only when no held copy exists, so a later writer cannot replace the owner the human was shown. `invite approve` and `invite deny` (and recovery) take a per-invite lock file (`<invite-id>.lock`, mode 0600, holding a random token of the holder) so two of them cannot both pair. The holder refreshes the lock every 30 seconds while it works; a held lock makes the other fail with `invite-busy`, a lock with no refresh for two minutes is taken over, the holder removes the lock only if it still holds its token, and `invite revoke` takes it too: while an approve or deny is working on the invite it fails with `invite-busy` ("Try again in a few minutes.", like every `invite-busy` message) and deletes nothing, and `watch` skips such an invite when it expires invites. A record read for revoke or expiry is checked again right before each change, so a stale view cannot close a finished invite. Every node call made while an invite is being decided (acceptB and its delegations, the node's key-value calls, the invitation-store delete) is abandoned after 60 seconds with `node-timeout`, leaving the invite held again as any other failure does. When the 60 seconds pass, `acceptB` is told to stop: it starts no new write (not the peer, not the peer record on the node, not `profile.json`; a write already on the wire cannot be recalled: after a deny, `me/peers/<handle>.json` on the node may still say `paired`, and Courier never reads it as authority), so an abandoned pairing step cannot pair a peer after a deny or overwrite a newer `profile.json`. A read grant that the abandoned step may already have asked the node for is written down in a private file (`<invite-id>.grant-<attempt>.json` in the invites directory, mode 0600, removed by `watch` once the grant could no longer be valid): `invite list` shows it as `possibleGrants`, `invite approve` shows it before pairing and reminds you after approve or deny, the held notice says a read grant from an earlier attempt may exist until a date, and the invite is held with reason `node-timeout`. The grant is not revoked automatically yet. A grant record is written only if `invite list` can read it back; one that cannot be recorded (a courier DID that is not an ed25519 did:key) is carried as a date without a courier (`unrecordedGrantUntil` on the private invite record: it only moves later, a re-hold or a retry does not erase it, and the sweep removes it once it has passed). Owner-facing texts print a hello's courier DID only when it is a real ed25519 did:key. Each move to consumed writes its own marker, and before every write that changes the invite (the artifact C, the Welcome, `completed`, `held`, `denied`, `failed`, `expired`, `revoked`; `watch` re-reads every invite before it closes or expires it) the holder checks that the invite on disk is still the one it consumed and that the lock is still its own; otherwise it stops with `invite-lock-lost` and writes nothing more. The invite-held notice now names the full `courier invite approve <id> --owner <owner>` command.
- `pair start`, `pair accept` and `join` refuse a handle that a peers file lists (`peers-entry-exists`; an unreadable file is `peers-unreadable`) before they create a peer or a grant, with the same `--peers-file` / `COURIER_PEERS_FILE` / default locations as `invite`.
- `invite` now prints guidance with the link: send it by a different channel than the invited email address (or add `--also-ask` / `--expect-owner` if it goes by email), and anyone who holds the link can read the inviter's owner address, space and handles until it expires.
