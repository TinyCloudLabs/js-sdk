`tinycloud onboard` and `tinycloud auth grant` accept `--timeout <Ns|Nm>` (more than zero, at most 9m; anything else is a usage error, exit 2 `INVALID_TIMEOUT`; `onboard` refuses it together with `--code`) to bound the wait for the owner's OpenKey approval. Exit 8 with `{"pending":{"step","of","approvalUrl","expiresAt"}}` on stdout is not a failure: it is printed at once when a new approval link exists (so an agent can send it to the owner immediately) and again when a resumed link is still unanswered at the timeout; run the same command again. An approval the owner already gave is never reported as pending: it is collected, verified and saved, and acknowledged, even past the timeout (up to 30 s more, plus up to 3 s and local work, so `--timeout 60s` ends in about 105 s at the most for an existing account; an acknowledgement whose reply is lost is re-sent with the same id on the next run). On a new account `onboard` also bounds its wait for OpenKey to host the space by the time left of the timeout plus the 30 s grace (at least 15 s) instead of 150 s, about 90 s in all for `--timeout 60s` and at worst a little under 2 minutes, and ends with the existing `SPACE_SETUP_PENDING` (exit 1): wait a minute and run it again; the re-run continues with step 2, and if a storage command later says `Space not found`, wait and retry. `onboard` has 2 steps, `auth grant` is step 1 of 1. An expired request is exit 3 (a stored request past its own expiry that holds no result is dropped without asking OpenKey, and OpenKey's HTTP 400 `invalid_request` answer for an expired request is exit 3 too, so the next run makes a new request with a new link; a 400 before the link's own expiry stays exit 8 `APPROVAL_REQUEST_UNAVAILABLE`), and OpenKey being unavailable is still its own exit 8 error without the `pending` object. Without `--timeout` nothing changes.
