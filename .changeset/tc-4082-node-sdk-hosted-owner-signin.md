"@tinycloud/node-sdk": patch

A third-party app can sign in for an owner whose account is hosted on the default node (`https://node.tinycloud.xyz`) but has no registry record, instead of failing with `ACCOUNT_SETUP_REQUIRED`. This applies only when the app asks for nothing beyond its own `applications` space and holds an uncaveated `tinycloud.kv/list` or `tinycloud.space/info` on it, with no other `tinycloud.space` ability and no ability ending in `create`. Data abilities such as `tinycloud.kv/put`, `tinycloud.kv/del` and `tinycloud.sql/write` don't stop it. After the owner's consent the SDK sends one `/delegate` to the default node and one read of that space (`kv/list` with limit 1, or `space/info`). A 2xx proves the space is hosted and sign-in continues. Any other answer returns `ACCOUNT_SETUP_REQUIRED`, clears the saved session and never sends a second `/delegate`; a network error, timeout or 5xx during the check fails with a non-setup error and the same cleanup. When the `/delegate` may have been accepted (it was accepted, or the answer was a 5xx, a network error or a timeout), the SDK also sends one `/session/retire` to the default node so the node does not keep that session; this is best effort, and overlapping sign-ins can misattribute it (TC-4154). A `/delegate` the node refused (4xx) is only discarded locally. No account, space or registry record is created; the node may keep the delegation until it is retired or reaches its signed expiry. The same read runs once when a restored session of such an owner first needs a route; a restored session the read refuses is removed from storage. Configured hosts are never used. Registered, first-party and unavailable-registry sign-ins are unchanged.

Details: TC-4082
